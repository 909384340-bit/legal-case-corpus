## 一、为什么选这个数据源

### 1.1 数据源简介

| 项目 | 内容 |
|---|---|
| 数据源 | 中华人民共和国最高人民法院官网 · 审判业务 · **指导案例**栏目 |
| 入口 | `https://www.court.gov.cn/shenpan/gengduo/77.html` |
| 内容 | 最高人民法院审判委员会讨论通过并发布的**指导性案例**（第 265—279 号） |
| 发布口径 | 官方统一发布，含关键词、裁判要点、基本案情、裁判结果、裁判理由、相关法条 |
| 采集时间 | 2026-09-11，案例发布日期区间 2025-08-28 ~ 2026-02-28 |
| 权威性 | 国家级（最高审判机关）官方一手来源 |

### 1.2 选择理由（对应课程「数据识别与价值判断」的四条标准）

1. **权威性最高**：指导性案例由最高人民法院审判委员会讨论通过，各级法院审判类似案件时**应当参照**。作为律师，这是可以直接写进代理意见的弹药，价值远高于二手解读、自媒体汇编。
2. **现行有效性可控**：官网栏目只保留现行有效的指导性案例（失效的会另行发布"不再参照"通知），从源头就降低了课程强调的"**效力管理**"成本。
3. **可回溯性强**：每篇都有固定 URL 和发布时间，元信息完整，符合课程要求的"可回溯"标准；日后复核、更新、剔除失效数据都有抓手。
4. **复用价值高**：结构高度统一（裁判要点 + 基本案情 + 裁判结果 + 裁判理由 + 相关法条），天然适合切片做 RAG 知识库、做要件式检索、做类案检索的对照组；也契合我自己的业务方向（刑事 + 民商事争议解决），本期 15 篇覆盖刑事危险驾驶、交通肇事、知识产权、个人信息保护、执行实施等类型。
5. **反"松鼠病"**：课程提醒"避免松鼠病式无效收集"。我只取一个栏目、一个批次、15 篇，宁可少而精，不做无目的囤积。

## 二、数据采集方法（脚本：`scripts/01_fetch.py`）

### 2.1 采集方式选择

课程讲了三种采集方式，本次采用**全自动（脚本采集）**：

| 方式 | 是否采用 | 说明 |
|---|---|---|
| 手工采集 | ✗ | 15 篇复制粘贴易漏、易错，且无元信息 |
| 半自动（网站批量下载） | ✗ | 该栏目未提供批量下载入口 |
| **全自动（脚本）** | **✓** | Python 标准库 urllib 请求 + 正则解析，一条命令完成 |

### 2.2 采集流程

```
列表页解析  →  详情页抓取  →  正文抽取  →  落盘 + 清单
77.html       /shenpan/      标题/发布时间/    data/raw/*.txt
77_2.html     xiangqing/     来源/正文         + manifest.json
77_3.html     {id}.html
```

1. **列表页解析**：依次请求列表页（首页 + 第 2、3 页），用正则提取 `/shenpan/xiangqing/{id}.html` 形式的链接与标题，按 URL 去重；
2. **详情页抓取**：逐篇请求详情页，提取 `<title>`（去除站点后缀）、发布日期（支持 `2025-08-28` 与 `2025年8月28日` 两种格式）、来源、正文区块（优先 `content / article / TRS_Editor / detail` 容器，失败则回退到"最长 `<p>` 段落集合"）；
3. **正文纯文本化**：去 `<script>/<style>`，`<br>`/`</p>` 转换行，去标签并还原 HTML 实体，全角空格/不间断空格归一；
4. **落盘**：每篇保存 `.txt`（正文 + 来源 URL/发布时间/采集时间）与 `.html`（原始页面留存备查），同时生成 `data/raw/manifest.json`（含 URL、标题、发布时间、采集时间、正文长度、SHA256 前 16 位），**实现可回溯与完整性校验**；
5. **断点续采**：已存在的文件自动跳过，重跑不会重复请求。

### 2.3 合规与节制（课程的合规要求）

- 单线程、每篇间隔 **1.2 秒**，不并发、不高频，避免对服务器造成负担；
- 仅采集**公开发布**的官方内容，不绕过任何登录或验证码；
- 用途限定为**个人知识库与学习研究**，不用于商业传播（已在每篇文件的 YAML 中写明 `usage` 与 `license_note`）；
- 原始 HTML 只留本地，**未脱敏的中间文件不进仓库**（见 `.gitignore`）。

## 三、数据清洗方法（脚本：`scripts/02_clean.py`）

课程要点是"**二进制/富文本 → 纯文本，消除格式噪音，增加元信息，结构化**"。本环节把网页语料加工成可直接喂给大模型的 Markdown：

| 步骤 | 具体做法 | 效果 |
|---|---|---|
| ① 格式转换 | HTML → 纯文本（采集时完成），本步再做 Markdown 结构化 | 消除标签噪音，提升解析准确率 |
| ② 去页面噪声 | 删除页眉页脚、栏目导航、"字号 / 小 / 大"、"打印本页"、"上一篇/下一篇"、责任编辑、来源与发布时间行、版权声明 | 15 篇共删除 **105 行**噪声 |
| ③ 标题去重 | 删除与标题重复的正文首行 | 避免大模型重复读取 |
| ④ 空白规范化 | 全角空格 `\u3000`、不间断空格 `\xa0`、零宽字符清理；行首行尾去空格；连续空行压缩为一行 | 统一排版 |
| ⑤ 板块结构化 | 将"裁判要点 / 基本案情 / 裁判结果 / 裁判理由 / 相关法条 / 生效裁判 / 关键词"提升为 Markdown 二级标题 | 便于后续**按语义切片**做检索 |
| ⑥ 元信息外置 | 把"来源 / 发布时间 / 采集时间"从正文移出，改由下一步写入 YAML Front Matter | 正文纯净，元数据结构化 |

清洗前后：原始 ~4.7 万字 → 清洗后 **43,745 字**，噪声行 -105，标题重复 -15。

> 课程还提到"**版本管理：定稿前用 Markdown + Git**"。本仓库即按此执行：全部内容为纯文本 Markdown，用 Git 管理版本；需要交付给别人时再转 Word/PDF。

## 四、脱敏处理方法（脚本：`scripts/03_desensitize.py`）

这是本次作业的**重点**。课程给出了四种脱敏方案，我把四种都用上并组合成流水线，而非只靠单一正则。

### 4.1 四种方案的落地

| 课程方案 | 本项目的实现 |
|---|---|
| **① 正则表达式** | 案号、身份证号、手机号、统一社会信用代码、银行账号、电子邮箱、车牌号、出生日期 |
| **② 词典匹配** | 内置司法实体词典（法院 / 检察院 / 公安 / 律所 / 公司 / 产品）+ 行政区划词典（省级 + 主要城市）；并设**泛称停用词典**（"公交公司""本公司""该公司"等不是特定主体，不脱敏） |
| **③ 规则 / NER** | 匿名化姓氏模式 + **频次确认** + **简称归并** + 后缀锚定向左扩展 + 越界截断 |
| **④ 大模型脱敏** | 脚本输出「拿不准的疑似实体」清单 `logs/llm_review_candidates.md`，由大模型（我）复核后写入 `data/llm_patch.json`，用 `--apply-llm` 回填，形成**人机闭环** |

### 4.2 关键工程细节（踩过的坑）

1. **匿名化姓氏模式 + 频次确认**：指导性案例里人名形如"黄某欢""罗某""艾某"。直接正则会把"黄某欢发现"整个吃掉。做法是：先用 `姓氏 + 某 + 0~1 字` 取候选，再统计**基础短名（姓氏某）的出现频次**，频次 ≥2 或出现在标题"X诉Y""X等"结构中才认定为当事人，最后取频次最高的完整形态；若完整形态以虚词或机构名常用字结尾，则回退到基础短名。
2. **后缀锚定 + 向左扩展**：机构名以"有限公司 / 公司 / 人民法院 / 律师事务所…"为锚点向左扩展，遇到标点或句法虚词停止，避免把"遂询问某信用账户运营商……"整句吞成机构名。
3. **越界截断**：候选名中若出现"诉 / 案 / 纠纷 / 判决 / 账户 / 用户…"等截断词，说明匹配越界，从**最后一个截断词之后截取**，而不是整条丢弃（否则会漏掉真名）。
4. **简称归并（一致性）**：`某信用管理有限公司` ↔ `某信用公司` 必须映射到同一占位符。采用两层归并——包含关系归并 + **核心名归并**（去掉"管理/有限/股份/科技/信息技术"等修饰后比较）。
5. **保护性替换**：《法律法规名称》与白名单机构（最高人民法院）先替换为内部 token，脱敏完成后再还原，防止被切碎（曾经出现过"最[审理法院01]人民法院"的翻车）。
6. **占位符保留上下文**：剥离掉的前缀虚词要保留（"通过某应用" → "通过[产品01]"，而不是 "通过" 凭空消失）。

### 4.3 脱敏口径（可解释、可审计）

**脱敏对象**（一律替换为一致性占位符）：

| 类型 | 占位符 | 数量 |
|---|---|---|
| 自然人（当事人、证人、第三人等） | `[自然人01]` | 292 |
| 法人 / 非法人组织 | `[法人01]` | 363 |
| 行政区划与地址（含省市县、路名、收费站等） | `[地点01]` | 180 |
| 审理法院（地方法院、专门法院） | `[审理法院01]` | 69 |
| 案号 | `[案号01]` | 47 |
| 产品与应用名（某应用、某平台） | `[产品01]` | 9 |
| 检察机关 / 侦查机关 | `[检察机关01]` / `[侦查机关01]` | 3 |
| 结构化敏感信息 | `[证件号码已删除]` 等 | 0（本批语料未出现） |
| **合计** | | **963 处** |

**保留内容**（说明理由）：

- **最高人民法院**：数据发布与溯源主体，属公共权威机构，且是判断案例效力的关键标注；
- **法律法规与法条名称**：非主体信息，且是法律推理的必备要素；
- **泛指主体**（"公交公司""本公司""该公司"）：不是特定法人，脱敏反而损害可读性，已加入停用词典。

### 4.4 映射表与再识别风险

- 同一实体在 15 个文件中**始终使用同一占位符**（全局映射表）；
- 映射表 `data/.masking_map.json` **不进仓库**（`.gitignore` 排除），避免"脱敏后仍能靠映射表反查"；
- 文件名也已中性化为 `01_gzcase-279.md` 形式，**主体名称不会残留在路径或标题里**；
- 未脱敏的原始层（`data/raw`、`data/clean`）同样不进仓库，仓库中只有脱敏成品、脚本与文档。

### 4.5 复核（方案四的实际执行）：脚本化 + 终审

`03` 脚本把"规则拿不准"的候选输出到 `logs/llm_review_candidates.md`（共 262 条），
由 `scripts/05_llm_review.py` 完成预分类，再由大模型（我）终审，结论落在 `logs/llm_review_result.md`：

| 判定 | 含义 | 数量 | 处理 |
|---|---|---|---|
| **A 泛指** | "公交公司""关联公司""前述两公司""所有员工和子公司"等并非特定主体 | 45 | **不脱敏**，已写入停用词典 `data/generic_terms.txt` |
| **B 官方已匿名** | "某传媒公司""西某软件公司"等，发布时已匿名化 | 33 | 规则层已整体映射为 `[法人xx]`，无需二次处理 |
| **C 待终审** | 多为句法碎片（"被告人艾某实""赔偿恒某科技公司"） | 180 | 逐条核对，**未发现遗漏的真实主体** |

**终审时的独立抽查**（不依赖脚本自查，直接对成品语料做反向扫描）：

```bash
grep -oh "[一-龥]\{2,12\}有限公司" data/final/*.md      # 结果：0 条真实公司全称
grep -ohE "(被告人|原告|审判员|书记员)[一-龥]{2,3}" ...  # 结果：仅"被告人供述""被执行人未履行"等非人名
grep -ohE "[（(]20[0-9]{2}[）)][一-龥]{1,10}号" ...      # 结果：0 条案号
```

即：成品语料中**无公司全称、无真实姓名、无案号残留**。

> 复核层的定位：课程列的第四种方案是"大模型脱敏"。我的体会是——**规则负责批量与一致，大模型负责兜底与纠偏**。
> 规则全量跑、可复现、可解释；大模型用来处理规则"拿不准"的边缘样本，防止误伤（如把"公交公司"当主体）。
> 两者不是替代关系，而是流水线上的上下游。

## 九、已知局限与后续

1. 指导性案例本身已做过一轮官方匿名化（"黄某欢""某信用公司"），本作业的脱敏是针对**残余可识别信息**（公司全称、法院、案号、地名、产品名）的二次处理；
2. 规则方案对**未匿名化的真实姓名**（如"审判员张三"）识别能力有限，已通过候选清单交大模型复核兜底；更彻底的做法是接入专用 NER 模型或大模型逐篇扫描（成本更高）；
3. 行政区划目前做到"省 / 市 / 区县 / 路名"层级，个别村级、小区级地名可能残留；
4. **网页标题折行**会导致跨行机构名未被整体识别（如"日某流量仪器 / 有限公司"被分成两行），残余部分为官方匿名化片段，不构成识别风险，后续可在清洗环节做折行合并；
5. 后续计划：把这批语料接入 Obsidian 双链知识库（课程推荐的 LM Wiki 思路），并按 `publish_date` 建立失效巡检机制（课程讲的**效力管理**）。
